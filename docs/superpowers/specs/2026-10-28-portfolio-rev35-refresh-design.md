# rev.3.5 기반 웹 포트폴리오 최신화 설계

## 목적과 기준

백엔드 신입 채용 담당자가 이은성의 역할, 문제 해결 과정과 실제 검증 범위를 빠르게 이해하도록 웹 포트폴리오를 정리한다. 최신 Notion 포트폴리오(407582168cf781c1931cc7f70763d548)와 표지 버전을 제거한 rev.3.5 PDF를 내용 기준으로 삼는다. 기존 HTML/CSS/JavaScript 정적 사이트와 자연어 도우미를 유지한다.

사용자는 화면·내용을 함께 재구성하고 기존 기술·자연어 도우미를 유지하는 방안을 선택했다. 이 문서는 구체적인 화면 구성과 변경 범위를 정리한 구현 전 설계다.

## 검토한 접근

1. 기존 화면에서 문구와 수치만 교체: 변경은 작지만 길고 반복되는 프로젝트 구성이 남는다.
2. **선택: 화면과 내용을 함께 정리:** 기존 기술과 도우미는 유지하고 정보 순서·여백·표·그림·모바일 배치를 조정한다. 데이터와 NLI 근거를 함께 바꿔 과거 수치가 다시 답변되는 문제를 예방한다.

React 등 새 프레임워크로 교체하거나 NLI 모델·서버 설정을 변경할 필요는 없다.

## 화면 구성

1. **상단 소개:** 이은성 / Java·Spring 백엔드 개발자, 간결한 소개, 기존 프로필 사진, GitHub·네이버 이메일·전화. 최상단에서 대표 프로젝트로 바로 이동한다. 공개 화면에는 rev 버전을 표시하지 않는다.
2. **대표 프로젝트 개요:** 사장님 피규어 → CateQuest → Bookking 순서의 3개 카드. 서비스 목적, 기간·역할과 핵심 경험을 보여주고 상세 위치로 연결한다.
3. **핵심 결과:** 최신 근거가 있는 캐시 DB 실행 수, DB 튜닝·앱 확장 종합 결과, N+1 개선을 짧게 표시한다. 각 수치 바로 옆에 로컬·단일 요청 등 범위를 붙인다. 실제 결과가 아닌 비용·HTTPS·CI 시간 절감 카드는 제거한다.
4. **프로젝트 상세:** 프로젝트별 목적·기간·팀·담당·기술·상태와 짧은 서비스/GitHub 하이퍼링크를 먼저 배치한다. 사례마다 핵심 결과, 문제·분석·행동·결과, 관련 표·그림과 시험 조건 순서로 통일한다. 상세는 기본적으로 열어 두어 검색과 도우미의 위치 이동을 유지한다.
5. **추가 경험:** 멘토링, 개인 도구 3개, 학력·교육·자격. 수상은 최신 이력서에 있는 확인된 2건만 사용한다. 개인 도구·교육 자료에는 용도를 알 수 있는 짧은 GitHub 하이퍼링크를 제공한다.

밝은 배경·짙은 글자·절제한 청록색 강조를 사용하고, 현재 한국어 글꼴과 도우미 색상 변수를 계승한다. 본문과 측정 조건을 구분하되 조건도 읽을 수 있는 크기로 둔다. 데스크톱은 넓은 본문과 간결한 제목 영역, 모바일은 한 열로 배치한다. 표는 모바일에서 자체 가로 스크롤하고 본문 전체의 가로 넘침은 막는다.

## 콘텐츠 범위와 사실 기준

- **사장님 피규어 4사례:** 메인 캐시, ARM 빌드·배포, PR 리뷰 보조, PostgreSQL 튜닝·앱 확장. 기존 관측성·비용·독립 CI 시간 절감은 이번 대표 사례에서 제외한다.
- 캐시 단일 요청 DB 실행 수 10→0회 / 1→0회. HTTP GET은 로컬 단일 클라이언트, MISS 200건·HIT 1,000건이다.
- ARM 에뮬레이션 빌드 최장 약 33분, 전환 후 빌드·배포 변경 규모별 약 1–10분. 동일 조건 개선율로 바꾸지 않는다.
- AI 리뷰 봇은 DB 변경·보안·로직 의심 지점을 알려주는 보조 도구다. 시간 절감 수치나 오류 차단 보장을 추가하지 않는다.
- DB는 약 8.6GB, 앱 2·4대 × 기본·튜닝 DB. 101.36→175.15 req/s(+72.8%), p95 2,013.00→1,279.16ms(-36.5%)는 **DB 튜닝과 앱 확장의 종합 결과**다. DB 1대 4 CPU/4GiB, 앱당 2 CPU/2GiB·풀 30, 혼합 60 VU, 최종 30초 조건별 1회와 4조건 표를 유지한다.
- **CateQuest 2사례:** N+1, 소형 모델 질문 생성. 프로젝트 DB는 MySQL, 종료 후 PostgreSQL17·일기50건·방식별15회 비교로 SQL53→1회, 조회·DTO 조립 중앙값7.785→1.557ms다.
- 질문 생성은 프론티어 모델로 만든 데이터셋과 polyglot-ko-1.3b LoRA 학습·로컬 생성이다. 실제 공부 카테고리 출력 3개, 제한된 다양성, 미배포·정량 품질 평가 미실시를 유지한다.
- **Bookking 1사례:** 프로젝트 이후 개인 개선, Facade 락·커밋 경계와 3가지 락 비교. 132회79,200요청=성공52,908+품절19,440+시간초과6,852. 재고·주문 불일치 미관측을 요청 전부 성공으로 바꾸지 않는다. 50명 확대군 표와 대기5초·고정임대1,000ms·풀50·인증/외부PG 제외를 유지한다. DB 비관적 락은 우선 검토 판단이며 운영 도입 완료가 아니다.

## 자연어 도우미와 기술 변경

`data/portfolio.js`를 화면과 Gateway의 공통 사실 데이터로 유지한다. 프로젝트/사례 ID는 의미가 같은 기존 ID를 재사용한다. 제거한 OTT·비용·HTTPS·관측성·CateQuest CI 항목의 경로와 용어의 관련 대상도 정리해 존재하지 않는 화면으로 이동하지 않게 한다. 해당 과거 실적에 대한 질문에는 최신 근거 없이 수치를 만들어 답하지 않는다.

표와 추가 경험도 도우미가 사용할 근거에 들어가도록 증거 구성 경로를 확인한다. 정합성·요청 성공·시간 초과, 종합효과·DB 단독 효과, 미배포·운영을 구분하는 회귀 사례를 둔다. 기존 이동 정책, 출처 버튼, 대화 안전 경계, 모델 호출 설정은 유지한다.

NLI/화면의 이전 내용을 전제로 한 fixture와 기대값은 최신 자료에 맞춘다. 보안 검증을 약화하거나 무관한 동작을 변경하지 않는다. 실제 모델 API/LAN 호출은 일반 검증에 포함하지 않는다.
