# Issue #12: Makertion 비용 설명의 분수 검증

## 관측과 원인

2026-09-20, 기준 리비전 `7a64df3`의 격리 worktree에서
`Makertion 비용 절감 내용을 설명해줘`를 빈 이력·현재 대상 없음으로
실제 LFM에 두 번 순차 요청했다. 기존 6,500ms/512-token/schema 설정에서
각각 약 3,139ms와 3,158ms에 HTTP 200/stop 및 전송 검증을 통과했지만,
공유 답변 검증은 두 번 모두 `quantity_unsupported`였다.
이는 수정 전 진단이다. 최종 구현의 수정 후 실측은 아래에서 별도로 구분한다.

실패한 최소 표기는 답변의 `1/20로`와 선택 출처
`project-makertion-cost`의 `기존 대비 1/20 수준`이다.
실제 전송한 2,999-byte 제한 근거 안에 분수가 남아 있었으며,
같은 답변의 `31%`와 `1분`은 이미 검증을 통과했다.
따라서 이 두 관측에서는 환각 수치나 출처 누락·잘림이 원인이 아니었다.

기존 파서는 양쪽 `1/20`을 숫자 `1`, 단위 `/20`, `valid:false`로 해석했다.
진단용 메모리 모듈에서 이 원자만 인식하도록 바꾸면 동일 답변·출처 ID·맥락·
제한 근거·payload의 전체 채택이 실패 → 성공 → 실패 → 성공으로 전환됐다.
이 진단용 예외는 제품 코드에 넣지 않았다. 원시 생성문·envelope·숨겨진 추론은
보존하지 않았으며 테스트에는 짧은 합성 문장만 사용한다.

## 보수적인 수정 범위

- 공유 숫자 파서에서 `[+−-]?[0-9]+/[0-9]+`를 하나의 **숫자**로 인식한다.
  부호 뒤와 slash 주변 공백은 허용하지만 분모는 0이 아니어야 한다.
- 기존 NFKC 정규화 이후 철자를 그대로 비교한다. 선행 0·부호를 유지하며,
  약분·소수 변환·Unicode fraction/division slash의 별도 치환은 하지 않는다.
  정수 `1`과 분수 `1/20`은 서로의 근거가 아니다.
- 인식 전에 분수처럼 보이는 전체 원자를 잡는다. 추가 slash, 소수/쉼표,
  분모 부호, 남은 비ASCII 숫자, 잘못된 단위를 지원되는 조각으로 재해석하지 않는다.
  `1/20.5`, `1/20/3`, `1//20`, `1/-20`, `1/0`, `1/000`은 자기 자신을
  근거로 제시해도 거부한다.
- 선행 slash와 말미의 Unicode slash도 버리지 않는다. `/1/20`, `1/20⁄`,
  `1/20∕s` 및 공백·혼합 반복 slash는 전체 오형식으로 거부한다.
  단위·조사 뒤의 `1/20ms∕s`, `1/20로⁄`도 같은 규칙을 적용한다.
  수집 범위만 넓혀 오형식을 유지하며 유효 숫자·단위 문법은 넓히지 않는다.
  정상 ASCII `1/20/s`, `30/s`는 유지하되 slash로 나눈 조각을 임의의
  독립 수치로 재해석하지 않는다.
- 실제 단위와 기존 한국어 말미 조사 처리·비대칭 단위 비교는 유지한다.
  단위 없는 주장은 같은 분수의 단위 있는 근거로 뒷받침될 수 있지만 역은 안 된다.
  뒤따르는 `31%`, `1분`도 각각 검사하며 기존 `31%1분` 오형식 거부는 유지한다.
- 기존 날짜 범위·수치/부호·출처 귀속 검증은 유지한다. 선택된 제한 근거만
  사용하며 다른 후보나 전체 맥락에서 삭제된 사실을 다시 가져오지 않는다.

## 검증 정책과 회귀

검증 binding은 validator 소스 자체를 해시하지 않으므로 의미적 수용 규칙을
`shared-acceptance-v2`로 올린다. **receipt 형식 version은 1 그대로**다.
명시적 v1 LFM report, Qwen report/receipt 및 내부 binding은 거부하며,
bound producer는 과거 결과에 새 정책을 붙여 재사용하지 않는다.
현재 v2 양성 대조군도 함께 검사한다. 배포 판단 전 새 정책의 fresh bound proof가
필요하며 기존 결과를 v2로 다시 표시해서는 안 된다.

숫자 단위 테스트와 합성 LFM/Qwen/probe 통합 회귀는 지원 분수의 채택,
변조·오형식의 거부, 선택 출처에 없는 분수의 거부를 검증한다.
새 통합 파일은 `tests/catalog.json`에 등록했다.
초기 구현 전 신규 회귀 포함 36개 중 11개가 실패했고, 초기 집중 테스트는
74/74 통과했다. 이후 리뷰가 선행 slash와 숫자가 뒤따르지 않는 Unicode slash를
스캐너가 버리는 우회를 발견했다. 경계 회귀를 먼저 추가한 결과 59개 중 9개가
실패했고, 수집 경계를 보정한 뒤 proof 회귀를 포함한 85/85가 통과했다.
이후 혼합 단위·조사·Unicode 숫자와 구분자 뒤 slash가 합쳐진 경우에도
유효 접두부가 남는 문제가 발견되어, 최종 구현은 `fraction-atom.mjs`의 작은
전용 스캐너로 전체 분수 범위를 소유하고 검사하도록 분리했다.
일반 scalar 정규식과 날짜 처리는 유지한다. 잘못된 분수의 내부를 다음 숫자로
재시도하지 않으며, 별도로 존재하는 정상 근거까지 무효화하지 않는다.
오형식은 공통 수용·probe에서 거부되고 일부 문장은 더 앞의 계약 검증에서
`proposal_invalid`로 거부되므로 모든 거부를 수치 검증의 결과로 세지 않는다.

최종 독립 집중 회귀는 146/146, 전체 Node 테스트는 179/179 및 380/380,
fake cascade는 17/17, catalog·구문·JSON 검사는 70개 등록 파일로 통과했다.
코드·안전성 재리뷰에서 앞선 우회 사례 및 추가 경계 검사도 통과했다.
LSP는 외부 worktree 경로 제한으로 사용할 수 없어 clean 진단을 주장하지 않는다.

## 최종 구현의 실서버 재확인

2026-09-20 17:14:25–17:14:32 UTC, `7a64df3` 기반 최종 미커밋 소스에서
같은 질문과 6,500ms/512-token/schema 설정으로 두 번 순차 호출했다.
소스별 해시가 실행 전후 동일했으며, 이후 이 문서만 결과에 맞춰 갱신했다.

| 경로 | 완료 | 답변 채택 | 시간 | fallback / timeout |
| --- | --- | --- | --- | --- |
| 실제 production LFM client | HTTP 200 / stop | 1/1 | 약 3,047ms | 없음 / 없음 |
| 격리 실제 Gateway → LFM | HTTP 200 / stop | 1/1, 최종 `lfm / accepted` | 전체 약 3,426ms, LFM 약 2,786ms | 없음 / 없음 |

두 답변은 `1/20`을 포함하고 `project-makertion-cost`를 선택했다.
원시 답변과 숨겨진 추론은 메모리에서만 다뤘고 공개 자료에는 저장하지 않았다.
Qwen은 격리 Gateway에서만 OFF로 두었으며 실제 Qwen 호출·자동 재시도·
서버 설정 변경·재시작·배포는 하지 않았다. 작은 표본의 해당 시나리오 확인이며,
fresh v2 bound proof, 다른 이슈 또는 전체 운영 readiness 검증은 아니다.

부모가 관측한 경계 보정 전 직접 요청 3/3·Gateway 3/3 채택은 **이전 dirty
snapshot의 실측**이며 현재 보정의 증거로 다시 표시하지 않는다.
이전 dirty snapshot의 결과를 최종 구현의 실측으로 합산하지 않는다.
